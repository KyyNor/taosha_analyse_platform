## 一、改造背景与动机

### 1.1 现状画像

在本次 17 次提交中，**后端逻辑**分布在 9 个功能模块。经调研，现有代码的单元测试覆盖率呈现出明显的二元分化：

| 层级 | 特征 | 典型代表 | 可 UT 性 |
|------|------|---------|----------|
| **纯函数层** | 无 IO、无 DB 依赖、入参明确、出参可断言 | `_compute_half_hour_slot()`、`TrendRequest` 校验 | ✅ 极佳 |
| **Schema 层** | Pydantic 构造/序列化、反序列化 roundtrip | `RiskControlModelCreate`、各 `BaseModel` | ✅ 佳 |
| **业务逻辑层（已解耦）** | 通过注入依赖 Mock，逻辑可独立运转 | 开关真值表、JSON 序列化/反序列化 | ✅ 良 |
| **高耦合业务层** | DB Session + Spark + PG DDL + 外部 API 混在一处 | `sync_service._diff_indicators()`、`hit_record_processor()` 合并逻辑 | ❌ 无法人工 UT |

目前已有 **165 个测试函数**，覆盖了前三类，**直接可运行的不需要任何改造**。

但第四类（高度耦合）中，有一些业务逻辑的价值非常高（如"增量同步的列分类"、"通知目标合并去重"），但被嵌在了重型依赖图中，难以被可靠的自动化测试覆盖，形成回归风险的盲区。

### 1.2 为什么要现在改？

```
改动前                          改动后
────────────────────────────    ─────────────────────────────
覆盖方式：人工回归               覆盖方式：CI/CD 自动回归
每次发布时间：≥ 4h 人工          每次发布时间：≤ 3min 机器
缺陷逃逸率：高（人工难免疏漏）    缺陷逃逸率：低（参数化穷举边界）
新增场景：需要开发配合造数据      新增场景：任何人加参数即可自动化
```

此外，本次提交中 **ALERT 和 WT 模块是 P0 级别的核心业务**，它们的回归质量问题直接影响生产。若不趁此次重构机会把它们纳入自动化测试套件，下一次的改动风险将是"看不见的黑盒"。

### 3.2 核心逻辑摘录（现状）

```python
# ---------- 当前代码（简化表达） ----------
def _diff_indicators(
    self,
    current_metadata: dict,   # {indicator_id: {version: int, indicator_code: str, ...}}
    target_metadata: dict,
) -> Tuple[list, list, list]:
    """
    返回：(changed_cols, new_cols, static_cols)
    分类依据：target.version 与 current.version 的大小关系
    """
    changed, new, static = [], [], []
    all_keys = set(current_metadata.keys()) | set(target_metadata.keys())

    for idx in all_keys:
        cur = current_metadata.get(idx)
        tgt = target_metadata.get(idx)

        cur_ver = (cur or {}).get('version')
        tgt_ver = (tgt or {}).get('version', 1)
        code = (tgt or cur or {}).get('indicator_code', '')

        if cur is None:
            new.append(code)           # ← Target独有 → 新增
        elif cur_ver == tgt_ver:
            static.append(code)       # ← 版本相同 → 静态，可COPY
        else:
            changed.append(code)      # ← 版本有升 → 变化，需PIVOT重建

    return changed, new, static
```

### 3.3 改造方案（新建 + 修改两步）

#### 步骤 A：在新目录中创建 `backend/domain/wide_table/version_delta.py`

```python
"""
backend/domain/wide_table/version_delta.py
==========================================

Domain 层：宽表版本之间指标的差异计算

职责
----
接收当前版本和新版本的 metadata 字典，计算以下三类列差异：
- static_cols  ：版本号未变，可直接 COPY（速度最快，利用 PG INSERT...SELECT）
- changed_cols ：版本号已升，需 Spark PIVOT + UPDATE 重建
- new_cols     ：新版中独有的指标，等同 changed_cols 的待遇

使用约束
--------
本模块为纯领域逻辑，无 IO，无外部依赖，可放心在任意测试中使用。
使用时，调用方负责确保 dict 的 key/value 形态符合接口约定（见下方 docstring）。
"""

from dataclasses import dataclass, field
from typing import Dict, List, Optional

from ....fraudhunter.indicator import IndicatorCategory  # 如已有 domain enum 则引用；暂无则新建 Literal


@dataclass
class VersionDelta:
    """两版本之间完整列差异的持有结构。"""
    static_cols:  List[str] = field(default_factory=list)
    changed_cols:  List[str] = field(default_factory=list)
    new_cols:      List[str] = field(default_factory=list)

    @property
    def is_unchanged(self) -> bool:
        """返回 True 时，增量同步应跳过（status: skipped）。"""
        return not (self.changed_cols or self.new_cols)

    @property
    def has_any_change(self) -> bool:
        return bool(self.changed_cols or self.new_cols)

    @property
    def deferred_cols(self) -> List[str]:
        """static 以外的其余列，都需要 PIVOT 重建（changed + new）。"""
        return self.changed_cols + self.new_cols


class WideTableComparator:
    """
    领域逻辑：将 current_metadata 和 target_metadata 转化为 VersionDelta。

    设计原则
    --------
    1. 完全无 IO（不使用 DB、文件、网络、外部服务）
    2. 参数和返回值均为Plain Old Python Objects（POPO，dataclass）
    3. 确定性强：相同输入在任何时候、任何线程下得到相同结果
    4. 可逆推：given 一个 VersionDelta，我们可以还原出等价的 current 和 target
    """

    @staticmethod
    def diff(
        current_metadata: Dict[int, dict],
        target_metadata: Dict[int, dict],
    ) -> VersionDelta:
        """
        入参约束
        ---------
        current_metadata: {
            indicator_id(int): {
                "version": int,                          # 必须
                "indicator_code": str,                   # 必须
                "indicator_name": Optional[str],         # 可选
                ...其他字段不影响分类结果...
            }
        }
        target_metadata: 同上（通常来自即将上线的版本）

        返回值
        ------
        VersionDelta(static_cols=[], changed_cols=[], new_cols=[])

        示例
        -----
        >>> current = {1: {"version": 1, "indicator_code": "A"}}
        >>> target  = {1: {"version": 2, "indicator_code": "A"}}
        >>> delta = WideTableComparator.diff(current, target)
        >>> delta.changed_cols
        ['A']
        >>> delta.is_unchanged
        False
        """
        changed, new, static = [], [], []
        all_ids = set(current_metadata.keys()) | set(target_metadata.keys())

        for idx in all_ids:
            cur = current_metadata.get(idx)
            tgt = target_metadata.get(idx)

            cur_v  = (cur or {}).get("version")
            tgt_v  = (tgt or {}).get("version", 1)
            cur_code = (cur or {}).get("indicator_code", "")
            tgt_code = (tgt or {}).get("indicator_code", "")
            code = tgt_code or cur_code  # 以 target 为准

            if cur is None:
                new.append(code)           # Target独有不存在于Current
            elif cur_v == tgt_v:
                static.append(code)       # 版本数字相等，静态度
            else:
                changed.append(code)      # 版本有升，变化列

        return VersionDelta(
            static_cols=static,
            changed_cols=changed,
            new_cols=new,
        )
```

**预计行数**：约 75 行（含 docstring、type hints、空行）

### 4.3 改造方案（新增一个公开静态方法）

#### 步骤：在 `model_hit_alert_manager.py` 中新增方法

```python
# 文件：backend/services/fraudhunter/model_service/model_hit_alert_manager.py

class ModelHitAlertManager:
    # ... 现有代码不动 ...

    # ───────── 新增内容（建议插在 hit_record_processor() 之前）───
    @staticmethod
    def merge_notification_targets(
        branch_notice_no: Optional[str],
        cm_targets: List[str],
        fin_targets: List[str],
    ) -> str:
        """
        将三种来源的通知号合并，去重后返回逗号分隔字符串。

        适用场景
        --------
        命中告警时，向分支行通知号（系统配置）、客户经理通知号（AcctAssign表）、
        理财经理通知号（CustOwner表）三类目标合并后，一次调用 send_alert_message()。
        本方法保证：
        1. 空字符串（branch_notice_no=""）和 None 不产生多余逗号
        2. 三路中出现的重复手机号/人名只出现一次
        3. 保持第一次出现的相对顺序

        参数
        ----
        branch_notice_no : 分支行通知号，可能是逗号拼接字符串、全局配置值、空字符串、None
        cm_targets       : 客户经理通知号列表，元素可以是逗号拼接字符串
        fin_targets      : 理财经理通知号列表，元素可以是逗号拼接字符串

        返回值
        -------
        逗号分隔的去重字符串，形如 "张三,李四,王五" 或空字符串 ""

        示例
        -----
        >>> merge_notification_targets('admin,A', ['B','A'], ['C','B'])
        'admin,A,B,C'

        >>> merge_notification_targets('', ['A'], [])
        'A'

        >>> merge_notification_targets(None, [], [])
        ''
        """
        all_sources = (
            ([branch_notice_no] if branch_notice_no else [])
            + list(cm_targets)
            + list(fin_targets)
        )
        flat = [
            item.strip()
            for source in all_sources
            for item in str(source).split(",")
            if item.strip()
        ]
        # Python 3.7+: dict 保证 insertion-order，正是"去重保序"的需求
        unique_ordered = list(dict.fromkeys(flat))
        return ",".join(unique_ordered)

    # ───────── 新增内容结束 ────────────────────────────────────
```

## 六、风险评估与缓解措施

### 6.1 公用风险识别

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 提取后原调用方意外断裂 | 低 | 高 | 方法签名保持完全一致（参数名、数量、类型、返回值）；写好 STEP 3 后用 git stash 保存工作目录，先跑 UT 验证 |
| 业务逻辑等价比对失败 | 中 | 中 | 提供完整的参数化真值表（见各自的验收标准节）；用同等数据运行新旧两版，比对输出一致 |
| 新文件 Python path 不对齐 | 低 | 中 | `backend/domain/wide_table/` 需添加到 `__init__.py` 或 `sys.path`，参考 Django 风格的包结构 |
| 部署后 import 报 `ModuleNotFoundError` | 低 | 中 | 在 `backend/__init__.py` 添加 `from .domain import wide_table`，或在 CI 中确认 sys.path 设置正确 |

### 6.2 测试风险识别

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 改造激活后发现边界行为与旧代码有细微出入（空格、unicode normalize 等） | 中 | 低 | 在 `version_delta.py` 的 docstring 中明确行为约定；在 UT 中明确标注哪些行为是"有意为之的改善"（如 strip 处理空白的规范化） |

## 八、FAQ

### Q1：为什么不直接把 `_diff_indicators()` 直接改成静态方法然后立刻测试，还要创建一个新的 domain 包？

**答**：创建 `backend/domain/` 而不是直接在 `utils/` 或 `services/` 中放置，是因为"领域层"是一个语义明确的概念——它表示**纯粹的、与技术设施无关的业务逻辑**。放在 `domain/wide_table/` 中，给未来阅读者一个明确信号：这块代码是可以无条件信任、不必担心隐蔽依赖的。相比之下，放在 `utils/` 容易被认为"这只是一个小工具函数"而被随意修改。

另外，这种分层在大型重构（比如将来引入 CQRS、Event Sourcing）时会显得自然，不用到时候再去搬代码。

### Q2：如果有人想在这两个方法里添加日志或指标埋点怎么办？

**A**：我们的策略是**不要在这里加**。"纯函数"的核心价值就是**无副作用、可信、可测试**。如果要加监控，请在**调用方**（即原有的 `sync_wide_table()` 或 `hit_record_processor()`）中加，那里已经有了日志调用。把监控逻辑和领域逻辑绑在一起，就失去了我们提取出来的目的。

如果业务上确实需要知道某个 delta 导致了多少列变更，可以在调用方做观测：
```python
delta = WideTableComparator.diff(current, target)
logger.info(f"[Sync] changed={len(delta.changed_cols)}, new={len(delta.new_cols)}, static={len(delta.static_cols)}")
```

### Q3：能不能直接把整个 `sync_service.py` 全部重构，改成完全可测试的样子？

**答**：可以，但那就不叫"最小侵入式改造"，而是"大型重构"。不在本次 scope 内。本方案的目的是**在不改太多、不引风险的情况下，把最有价值的一小块逻辑解锁**。剩下的重度耦合部分（WTI-R01/02/06/07）建议通过集成测试+E2E 来覆盖，将来有时间再做 Strategy 模式的接口解耦。

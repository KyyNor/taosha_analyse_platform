FraudHunter 次级模型 · 技术方案 v2

在现有「指标 → 宽表 → 模型 → 告警」四层架构之上，引入扩散规则节点实现二跳判定（嫌疑人扩散 / 受害人扩散）， 并把试运行（testing）状态开放给所有模型，实现"只命中、不告警、只记录"的灰度上线。 扩散口径（交易类型/方向/金额）作为规则节点在 RuleBuilder 里配置，运行时直接查现有流水表，不新建表。

01

业务背景与核心诉求

现状：单跳命中，直接处置

当前模型执行链路是单跳的：账号指标命中某 online 模型后，立即进入「命中 → 告警 → 管控」流程 （realtime_indicator_job.step3_hit_record → model_hit_alert_manager.hit_record_processor）。 模型间平行，互不联动；状态机只有 draft / online / archived 三态，没有灰度观察期。

新诉求一：基于命中结果做二跳扩散

🎯 嫌疑人扩散（多跳洗钱）

账号 A 被嫌疑人模型命中。则 A 的交易对手（如同银行出账目标 B、C）极可能也是嫌疑人 —— 规避监管的多跳转账。
源=嫌疑人模型 → 扩散规则（出账） → 疑似嫌疑人

🎯 受害人扩散（被骗转账）

账号 A 被受害人模型命中。则 A 的交易对手 B 极可能是嫌疑人 —— 受害人被骗向嫌疑人转账。
源=受害人模型 → 扩散规则（出账） → 疑似嫌疑人

新诉求二：通用试运行（所有模型可用）

次级模型依赖全部源模型结果，无法传统回测（计算量指数膨胀）。但"无法回测"的痛点不只次级模型—— 任何新模型上线都缺乏灰度观察期。因此试运行状态应对所有模型通用： 参与 realtime 匹配，能产出命中记录，但不告警、不管控、只记录，验证 OK 后转正。

✅ 核心诉求小结（v2） ① 扩散能力作为一种规则节点，在 RuleBuilder 里配交易类型/方向/金额； ② 试运行状态通用化，所有模型（normal + 扩散）都能试运行； ③ 不新建表，运行时现查现有流水表； ④ 转正 UI 二次确认，无审批流。
02

核心概念：扩散规则节点 + 通用试运行

2.1 扩散模型 = 普通模型 + propagation 规则节点

v2 不再引入 model_type='secondary' 这种独立类型。一个模型是否是"扩散模型"，由它的 RuleConfig 是否包含 propagation 节点决定。 这完全符合"一切皆规则"的现有设计哲学，配置入口统一在 RuleBuilder。

🔹 propagation 节点（新增）

规则树里的一个特殊节点，语义："对当前命中账号，沿某种交易关系扩散到对手方账号，并对对手方施加子规则"。 配置项：方向（出账/入账）、交易类型、金额门槛、是否同银行、时间窗。

🔹 扩散起点声明

propagation 节点上游通过 model_ref（现有机制）声明扩散起点的源模型。 后端自动从规则树提取依赖的源模型 ID（类似现有从规则提取 indicator_codes）。

2.2 通用试运行（testing 状态）

能力说明
适用对象所有模型（normal 模型 + 含 propagation 的扩散模型）
执行参与 realtime 匹配链路（Step2 / Step2.5），正常产出命中
告警/管控跳过——不调 hit_record_processor 的告警/管控分支
记录命中照常写入 HitRecord，标记 is_trial=true
转正UI 二次确认 → 转 online，无需审批
💡 为什么 testing 通用化是好设计 现有状态枚举注释里早就写了 draft/testing/online/offline/archived，但 testing 从未被启用。 v2 激活它并开放给所有模型，顺带补齐了 normal 模型缺失的灰度能力——一鱼两吃。 实现上只需在 realtime_indicator_job:356 的 filter 放开 status.in_(['online','testing'])， 并在 step3 加 testing 抑制分支。
03

不建表的硬约束与对策

你要求不新建表、运行时现查流水。我已核实流水表 realtime_oss_inct_new 的真实情况，有两个必须先对齐的硬约束：

约束一：对手方账号 cp_acct_no 没有索引 ⚠️

现有索引定义位置扩散查询用得上吗
idx_realtime_tran_date (tran_date)analyze_db_utils.py:344部分（分区裁剪）
idx_realtime_acct_no (acct_no):345是 出账方向扩散（按本方账号查）
idx_realtime_created_at (created_at):346否
cp_acct_no——缺索引 入账方向扩散（按对手方查）会全分区扫描
对策：不建新表，但在现有表上补索引（这是改表不是建表） 建议追加：CREATE INDEX idx_realtime_cp_acct_no ON realtime_oss_inct_new (cp_acct_no); 以及复合索引 (acct_no, tran_date) / (cp_acct_no, tran_date)。 分区表上索引建在父表会自动下推到各分区。这条不改的话，入账方向扩散会拖垮实时任务。

约束二：流水表默认只保留 14 天 ⚠️

配置项 fraudhunter_realtime_data_retention_days=14（config.py:253）， 清理任务 postgres_data_cleanup_job 会 DROP 超期分区。 意味着扩散只能回溯近 2 周的交易。

对策：按需调大保留期，或接受 14 天窗口 如果业务需要更长扩散历史，调大 data_retention_days（代价是磁盘占用增加）。 本期建议先用默认 14 天，propagation 节点的 time_window_days 也限制在 ≤14。

约束三：金额字段名与交易类型枚举

  • 金额字段是 inct_01_amount（decimal），不是 amount——规则引擎对接时别写错字段
  • tran_type 是 varchar，无正式枚举约束（测试脚本里有"转账/存款/取现/消费/代发/退款"，但生产值由上游 Kafka 决定）——配置交易类型时需先 SELECT DISTINCT tran_type 探查真实取值
✅ 结论 不建表可行，但必须补 cp_acct_no 索引（这是性能底线），并接受 14 天回溯窗口。 其余字段流水表都已具备。下面所有设计都基于"运行时 JOIN 现有流水表"。

4.2 Step 2.5 扩散匹配核心 SQL（运行时现查流水表）

-- 伪 SQL：propagation 节点的扩散匹配
-- 输入：source_hits = Step2 中被 model_ref 声明的源模型命中的账号集合
--       propagation_config = 从规则节点提取的扩散口径
--       target_rules = propagation 节点里的子规则（对扩散目标的指标条件）

WITH source_hits AS (
    -- Step2 命中且命中模型包含 propagation 上游 model_ref 指定的源模型
    SELECT account_id AS src_acct, model_hit_array AS src_model_hits
    FROM step2_matched_df
    WHERE array_overlaps(model_hit_array, :source_model_ids)
)
-- 直接 JOIN 现有流水表做扩散（出账方向示例）
SELECT
    t.cp_acct_no     AS target_account_id,   -- 扩散目标 = 流水对手方
    h.src_acct       AS trigger_account_id,  -- 溯源：源命中账号
    h.src_model_hits AS trigger_model_ids,
    SUM(t.inct_01_amount) AS propagation_amount,
    ARRAY[:propagation_model_id] AS model_hit_array
FROM source_hits h
JOIN realtime_oss_inct_new t   -- ★ 现查现有流水表，不建新表
  ON t.acct_no = h.src_acct         -- 出账方向：本方=源账号
WHERE t.tran_date >= :today - :time_window_days   -- ★ 必须带日期，触发分区裁剪
  AND t.tran_date <= :today
  AND t.inct_01_amount >= :min_amount            -- 金额门槛
  AND t.tran_type IN (:tran_types)                 -- 交易类型过滤（规则节点配置）
  AND ( :same_bank_only = FALSE OR t.cp_bank_num = :our_bank_no )
GROUP BY t.cp_acct_no, h.src_acct, h.src_model_hits
-- 结果再 JOIN 宽表施加 target_rules（rule_engine 生成的 WHERE）：
-- JOIN dep_acct_realtime_indicator b ON b.target_id = target_account_id
-- WHERE ( target_rules 编译出的 SQL )
💡 关键洞察 出账方向扩散用 acct_no（已有索引）；入账方向扩散用 cp_acct_no（需补索引）。 所有扩散查询都强制带 tran_date 范围，否则无法裁剪分区、会扫 14 天全量。 扩散结果与 Step2 主命中结构同构，多出 trigger 溯源字段，Step3 可统一处理。

4.3 试运行（testing）的数据流差异

testing 状态（所有模型）

参与 Step2/2.5 匹配 → 写入 HitRecord（is_trial=true）→ 跳过 Step4（不调 hit_record_processor 的告警/管控分支）→ 不产生 AlertControlRecord。 命中数据在「试运行监控视图」查询。

online 状态

参与 Step2/2.5 → 写入 HitRecord → 走 Step4（按 is_send_alert_message / is_acct_control 产生告警/管控）。 与现有 normal online 模型处置路径完全一致。

7.3 规则引擎的两种执行模式

普通模式 RuleConfig 不含 propagation 节点 Step2 现有批量匹配 4 表 JOIN + WHERE（现有 _build_model_matching_sql）
扩散模式 RuleConfig 含 ≥1 个 propagation 节点 Step2.5 新增扩散匹配器 源命中 JOIN 流水表扩散 + 目标宽表 WHERE

8.2 关键代码骨架：PropagationExecutor

# backend/services/fraudhunter/model_service/propagation_executor.py（新增）
class PropagationExecutor:
    """Step2.5：对含 propagation 节点的模型做扩散匹配"""

    def run(self, primary_matched_df, propagation_models, db):
        if not propagation_models:
            return empty_df

        all_secondary_hits = []
        for model in propagation_models:
            # 1. 从规则树提取 propagation 节点 + 上游 model_ref 的 source_model_ids
            prop_nodes, source_ids = parse_propagation(model.rule_config)

            # 2. 从主命中筛出被源模型命中的账号作为扩散起点
            source_hits = primary_matched_df[
                primary_matched_df.model_hit_array.apply(
                    lambda arr: set(arr) & set(source_ids))
            ]
            if source_hits.empty: continue

            for prop in prop_nodes:
                # 3. 直接 JOIN 现有流水表扩散（不建新表）
                propagated = self._propagate_via_txn(source_hits, prop, db)

                # 4. 对扩散目标施加 target_rules（复用 rule_engine.generate_sql_expression）
                matched = self._apply_target_rules(propagated, prop.target_rules, db)

                # 5. 补溯源字段
                matched['trigger_account_id'] = propagated.src_acct
                matched['is_propagation_hit'] = True
                all_secondary_hits.append(matched)

        return concat(all_secondary_hits)

风险与边界

风险等级应对
入账方向扩散性能（cp_acct_no 原无索引） 高 必须先补 cp_acct_no 索引（见 5.3）；查询强制带 tran_date 裁剪分区
流水仅保留 14 天，扩散回溯受限 中 接受 14 天窗口；或调大 data_retention_days（增磁盘）。propagation.time_window_days ≤ 保留期
扩散雪崩：一个源命中账号有大量对手方 高 propagation 设 min_amount 门槛；单源账号扩散目标数上限（如 ≤100）；试运行期观察尖刺
性能：扩散 JOIN 拖慢 30 分钟实时任务 中 补复合索引；监控 Step2.5 耗时，超阈值告警；必要时异步化
循环扩散（A→B 后 B 又触发源模型再扩散） 中 本期单跳：target_rules 内禁止嵌套 propagation；含 propagation 的模型不能被别人 model_ref
误扩散（工资代发、还贷等正常转账） 中 这正是试运行的价值——抽样复核发现并加 tran_types/min_amount 门槛
tran_type 无枚举约束，配置易写错 低 前端交易类型多选用 SELECT DISTINCT tran_type 动态加载真实值，不让手输
跨行对手方（cp_bank_num ≠ 本行） 低 same_bank_only=true 时过滤；跨行需外部数据，留作后续
转正后效果劣化 中 支持 online→testing 降级回退；告警记录页持续监控准确率
🚫 本期明确不做（边界） ① 多跳扩散（A→B→C）；② 跨行扩散；③ propagation 嵌套；④ 扩散模型离线回测； ⑤ 自动转正（必须人工二次确认）；⑥ offline 状态（用 archive 替代下线）。
